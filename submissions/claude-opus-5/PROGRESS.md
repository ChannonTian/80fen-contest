## ⚠ 第 41 轮起:主线换成时间预算(这是个淘汰门槛,不是优化项)

这是**淘汰门槛**,不是加分项。被刷掉损失 100%,而再挤 +0.05 级差几乎不值钱 ——
不对称风险,所以优先级压过一切棋力工作。

**基准选手是谁不知道**(README 第 255 行:主办方"安插一个基准选手一起打,
它和你们一样受同样的规则约束")。可以推出下界:如果它是 naive 级(1.3µs),
3× = 3.9µs,连 greedy 自己(5.9µs)都过不了 —— 那条规则就成了"任何认真思考的
程序都出局",不合理。**所以按 greedy 那一档定标,目标 ≤3×,留余量做到 ~2.5×。**

### 测量方法(先修这个,不然全是幻觉)

容器 CPU 有争用,greedy 自己单次读数在 4.8–8.3µs 之间跳。单次计时给出过
"2.53× greedy,已进线"—— **是假的**。正确做法(`dev/budget2.js`):

* 交替多轮,每轮所有选手各跑一遍同一批牌
* **轮内配对求比值**再取中位数(消掉牌的难易 + 机器漂移两个方差源)
* 要配对的两个必须**排相邻**,否则轮内漂移会灌进比值

### 统计口径:用最小值,不用中位数

这一条比上面四个改动都重要。容器有 CPU 争用,**观测时间 = 真实时间 + 非负噪声**,
所以多轮取**最小值**才是真实成本的估计。中位数会被噪声整体抬高,而且抬多少取决于
当时的争用强度 —— 不同批次之间根本不可比。前后几次读数在 2.53× 到 4.14× 之间乱跳,
全是这个原因。`process.cpuUsage()` 试过,380ns/次太贵,对 5µs 的 greedy 是 +15%
偏置,而且方向对自己有利,不能用。

### ⚠ 更正:「已合并版超线」这个结论是错的

上面那些 3.4×/4.1× 的读数**全部作废**,它们同时踩了两个坑:

1. **wall clock 在有争用的容器里量微秒级调用不成立。** 更糟的是比值本身会被
   争用推高 —— 调用越长越容易被中途调度出去,所以长调用膨胀得比短调用多。
   同一份代码前后量到过 2.76× 和 3.90×。
2. **标尺自己在跟着我变快。** `dev/bots.js` 里的参照选手 `require('../moves.js')`
   —— 也就是**我正在优化的**着法生成器。我每优化一次共享代码,greedy 也跟着
   快;而同样的绝对省时,对 12µs 的 greedy 是一大截、对 33µs 的我只是一小截,
   **比值反而变差**。我一度以为好几处优化"量不出来",其实是尺子在缩。

修法(`dev/corpus.js` + `dev/frozen/`):

* 录一份固定的决策位置语料离线重放,用 `process.cpuUsage()` **按批**计时 ——
  CPU 时间不算被调度出去的部分,按批又摊掉了 380ns/次的调用开销
* **每个选手录自己的局** —— 裁判量的是各自打自己的局的总时间,拿别人的局面
  喂它没有代表性(pointHog 在 baseline 的局面上量出 1.57×,自己的局里只有 0.99×)
* **标尺跑在冻结的引擎上**(`dev/frozen/`,永不更新)。真正的基准选手用主办方
  自己的引擎,不会因为我优化而变快。验证:`greedyFrozen` 与 `greedy` 对打
  级差 0.0000、行为差异 0.0%,冻结引擎下出完全一样的牌。

### 第三个坑:便宜的标尺预热不足会虚高

用冻结标尺第一次测出「baseline 2.89×,原来没超线」—— **那也是假的**。
`greedy(冻结)` 当时读作 11~14µs 且在批次间跳 27%。原因是它便宜,一批只有
~42ms,固定轮数下 JIT 没热透、按批的固定开销也摊不掉,**读数系统性虚高**。
分母虚高 → 倍数虚低 → 看起来安全。

最终的测法(`dev/corpus.js`),两层都要:

* **内层**按累计 CPU 时间自适应轮数(跑够 1.2s 再停),便宜的选手自然多跑几十轮
* **外层**取三次的最小值(观测 = 真实 + 非负噪声)

只做内层,噪声会从分母搬到分子(我的 AI 轮数少,变成 11% 跳)。两层都上之后,
两次独立运行的每一行都吻合到 1~2%。

### 采纳:`rolloutMargin 50 + maxCards 5 + K8 M6`(+0.0113 级/局,3.0σ)

时间预算榨出来之后,加深 rollout 从"买不起"变成了"买得起一档"。

`rolloutMargin` 值得单独说,因为它**不是**我一开始以为的那种「领先就跳过」闸门:
门槛越大,落在门槛内的候选越多,**精算的候选数反而增加** —— 所以时间对它是
**非单调**的(mg50 20.8µs,mg100 23.2µs)。棋力则是单调递增的,因为它只是少做

## 最重要的一课:自对弈 A/B 对「两边一起变差」结构性失明

这一轮做中前期领出前瞻(midLook),量到 **+0.059 级/局(5.5σ, n=2500)** ——
是整个项目里第二大的单点增益。然后拿它去和参照选手打,发现**我输给 greedy 0.48 级/局**
(之前一直是赢 0.38)。

**根因**:我用 Python 的 `str.replace` 往 `leadV2` 里插入 midLook 的两行,
而那段锚点文本

```js
    if (useRoll) scored.push({ cd: cd, sc: sc });
    if (sc > bestScore) { bestScore = sc; best = cd; }
  }
```

在 `leadV2`、`followV2` 和两个旧版 v1 函数里**一模一样**。`str.replace` 默认替换
**全部**匹配,于是 `if (useMid) scoredMid.push(...)` 被同时插进了 `followV2` ——
那里 `useMid` 根本没有声明。

后果链条:
1. `followV2` **每一次跟牌**都抛 `ReferenceError`;
2. `makeAI` 里的 `try/catch` 把它静默换成 `forceLegalFollow`(最笨的合法着法);
3. 于是**零违规、零罚分、局照打**,所有合规检查全绿;
4. 而**自对弈 A/B 完全看不见** —— 因为对照组也一样残,两边的 follow 都被打回原形。
   在「跟牌全废」的世界里,领出前瞻当然显得特别值钱。

修好之后重测:**midLook 是负的,−0.047 级/局(6.3σ)**。那 +0.059 从头到尾是假的。

顺带查出**同一个 bug 模式在更早的 rollout 补丁里就存在**(`useRoll`/`scored` 也被插进了
两个 v1 函数),只是 `evalV2` 默认开、那两个函数从不执行,所以一直是哑火状态。

### 留下的三道防线

1. **兜底计数器**:五个方法的 `try/catch` 和「主路径结果没通过校验」都记一次数,
   挂在 `ai.fallbacks` 上。`dev/bench.js` 每一行都打印它,不是 0 就是有东西在抛异常。
   这个 bug 如果早有这道防线,第一次跑 bench 就会暴露。
2. **每次改动都要对固定外部参照跑一次 bench**,不能只信自对弈 A/B。
   自对弈只能量「相对变化」,量不到「一起退化」。
3. 用 `str.replace` 改代码时,锚点必须**在整个文件里唯一**;
   插入位置在多个同构函数里重复出现时,这是必然踩的坑。

## 一个方法论教训:否定结论会过期

`followCap` 加宽在 n=600 的旧基线下量到 −0.4σ,在现在的基线下是 **+3.1σ**;
`dynTempo` 从 +0.2σ 变成 **+3.4σ**。基线换了之后,同一个改动的符号会翻。

所以「退回」不等于「永远错」。每隔一段时间应该**把否定过的想法整批重测一遍** ——
这一轮重测九个旧结论,捞回来一个真的。

另一个相关的坑:参照选手 `sibling` / `siblingR` 原来是 `makeAI({...})`,
没写到的开关会**继承 DEFAULTS**,于是我每次改进它们都跟着变强,
把「对同门对手的优势」系统性量小了。现在改成引用 `dev/yardstick/` 的冻结快照。

## rollout 的取舍(为什么停在 ≤4 张)

先用**探针**量清楚头部空间,再决定要不要建:

| 探针 | 值多少 |
|---|---|
| 完美**对手模型**(把「压不压得住」换成真答案) | +0.153 ~ +0.205 |
| 完美信息**走子**(≤4 张 / ≤8 张) | **+0.073 / +0.130** |

完美走子远大于完美对手模型 → **瓶颈是前瞻深度,不是概率模型**。这解释了为什么
mcModel / handModel / ruffFix 三次改进概率模型全部无效。

合法版:按各家剩牌数 + 已知断门采样一致的世界,只对**静态分最高的几个候选**走子到底。
(先按静态分筛掉再精算这一点很关键 —— 直接对所有候选做采样走子只值 +0.022,
筛过之后是 +0.030,因为采样噪声会把本来就烂的候选抬上来。)

最终的强度/耗时前沿(相对当前配置,n=2500;耗时是同一次运行里和 greedy 比):

| 配置 | Δ级差 | µs/决策 | 相对 greedy | 一场 |
|---|---|---|---|---|
| 不开 rollout | −0.039 | 25.1 | 2.96× | 75 ms |
| ≤3 张 | −0.018 | 28.6 | 3.36× | 86 ms |
| **≤4 张(采用)** | **0** | **33.8** | **3.98×** | **101 ms** |
| ≤5 张 | +0.011 | 42.6 | 4.52× | 128 ms |

每微秒的性价比很不均匀:**第一段(不开→≤3)只花 2~3µs 就买到 +0.021**,
往后每一段都越来越贵。≤4→≤5 是最差的一段(10µs 换 +0.011)。

**为什么停在 ≤4**:硬规则是「超出基准选手 3 倍不进决赛」,而我不知道基准选手多快。
`greedy`(刻意写得笨、但仍然做完整合法着法生成的对照选手)是 8.5µs。
* ≤4 = 34µs,只有在基准选手 <11µs 时才超标;
* ≤5 = 43µs,基准选手 <14µs 就超标。

被取消决赛资格是全损,而 ≤4→≤5 只值 +0.011(约等于我对同门对手优势的四分之一)。
**风险调整之后 ≤4 是拐点。**
如果日后确认基准选手不慢(≥15µs),把 `rolloutMaxCards` 改成 5 就能拿回 +0.011,
一个数字的事。

(margin 门控试过:省 25% 时间但砍掉 80% 的增益 —— rollout 的价值恰恰在于**推翻**
静态分的明显偏好,不在于打破平局。)

## 崩溃面 fuzz(`dev/fuzz.js`)—— 抓到「兜底自己会抛」

联赛里抛一次异常就是灾难,而我唯一的防线是五个方法外面的 try/catch。这条防线
**从来没被验证过**。写了针对性 fuzz:1040 个畸形/极端 view(手牌 0/1/33 张、
无主局、空历史、重复 id、越界点数、手牌里混 `null`)、5080 次调用,查三件事 ——
异常有没有逃出 try/catch、兜底返回的着法合不合法、冻结的 view 有没有被改写。

**第一版就抓到真问题:124 次异常穿透。** 三处兜底都写在 `try` **之外**,手牌里
混进 `null` 时兜底自己又抛一次;`follow` 更靠前的 `E.classify(plays[0].cards)`
也裸露着。**兜底路径存在的意义就是接住「没想到的输入」,一个自己会抛的兜底不
算兜底。**

加了 `lastResort`:只做最小假设的切片,永不抛。它返回的着法可能非法(吃罚分),
但**罚分是有界损失,异常不是** —— §S2 下抛异常直接记违规,而且走的是我控制不
了的路径。修完:逃逸 0 / 非法 0 / 改写 0,正常对局逐位不变。

`fallbacks` 加了 `hard` 计数。fuzz 里它被触发 **722 次** —— 说明第二层
(`forceLegalLead` / `forceLegalFollow`)在这些输入下也失败了,这一层不是冗余。

## 重入审计(`dev/reent.js`)—— 提速引入的新风险类别

这一轮的提速往 `engine/moves/strategy` 里加了不少**模块级可变状态**:版本戳表
(`_seen`/`_stamp`/`_cSeen`/`FSEEN`)、下标表(`IDX`/`FIDX`/`LIDX`)、复用的走子
手牌缓冲(`_PH`)、`analyze` 的复用缓冲区。

它们**全部依赖同一个前提:对应的函数不会自嵌套**。这个前提一旦破了,不会崩、
不会报错,只会静默算错 —— 丢掉合法候选,或者走子读到别人的手牌。正是最难发现
的那一类。

第一次检测只在导出对象上包了一层,**不够** —— 模块内部调用走局部函数名,绕过
包装(`genFills` 显示被调用 0 次就是证据)。定论做法是把三个文件复制一份、在
**函数体内部**插入深度计数再跑对局。结果:**21 个函数最大自嵌套深度全是 1**。

做成了可重复的工具,改完核心代码就重跑:`node dev/reent.js 40`。

顺带把另一个别名风险也验证掉了:走子里改成原地压缩之后,如果着法生成器返回的
数组就是手牌数组本身,就会边遍历边改。实测 11 万次生成器调用,`返回值 === 传入
手牌` 的次数为 **0**。

三个已经拆掉的静默炸弹(都不报错、只会悄悄变弱):

| 炸弹 | 触发条件 | 处理 |
|---|---|---|
| 版本戳回绕 | `Int32Array` 里的戳超过 2³¹,一场联赛能调上千万次 | 加回绕保护(`_stamp` / `_cStamp` / `FSTAMP` 三处) |
| 位掩码下标越界 | 手牌 >31 张(庄家扣底时是 33 张) | `useMask` 判断,超了退回字符串键,并用 33 张手牌验过退化路径 |
| 掩码键漏牌 | `genFills` 里出现不属于 `rest` 的牌 | 配版本戳表判归属,不属于就退回字符串键 |

## 连续减半:一个**代数上就赚不到**的否定结论

均摊搜索量的旋钮全部榨干之后(见下条),试了「同样预算用得更好」:连续减半 ——
早轮用很少的世界淘汰明显没戏的候选,把样本留给最后两个。

**赚不到,而且原因是代数的,不是调参没调好。** 等预算分配下,决赛候选拿到
`budget/2 = m·K/⌈log₂m⌉/2` 个世界,均摊版每个候选拿 `K` 个。要占便宜需要
**m > 2·⌈log₂m⌉** —— 而 `rolloutM: 6` 时 6 = 2×3,**恰好取等号**:决赛候选拿到
的正好也是 8 个世界,一模一样。

实测坐实了这一点:`rolloutSHW` 取 16 / 24 / 32,三组结果**逐位相同**(世界池
根本用不到),n=1500 量到 −0.0017。m 要到 8 以上才开始有赚,但 `rolloutM` 一
放大总预算就撑不住。

**顺带一个教训**:第一版用**常数** step(每轮世界数相同),量到 +0.0077(1.6σ),
一度以为成了。其实那是把最大预算花在候选最多的第一轮上 —— 总走子数 62 次 vs
均摊版 48 次。**涨的是预算,不是算法。** 一个"算法改进"如果没有把计算量钉死,
量到的多半是计算量。

### 同批重测的八个旧否定结论(n=1500,配置大改之后)

`rolloutSmartFollow` −0.0040 / `rolloutRichLead` −0.0017 / `leadDepth6` 0.0000 /
`leadDepth7` −0.0080 / `K10` +0.0013 / `M8` +0.0003 / `kittyPrior6` −0.0027 /
`kittyPrior2` +0.0017 —— **全部 ≤1.5σ,旧结论在新配置下依然成立**。

## 卡住的地方

1. **对手模型到了信息上限。** 闭式 / 蒙特卡洛 / IPF 三个完全不同的模型,Brier 都停在

3. **权重空间饱和。** 最近约 40 个方向的扰动全部 ≤1.5σ。
4. **必打关卡(`levels`/`played`/`gates`)是唯一没用上的信息通道,但推理下来几乎没有内容**:

   落袋的、不会再丢**,所以「已经拿到 80 之后要不要保守」根本不是一个决策。
   唯一真的有区别的是:闲家被关卡卡住时,庄家不必再去守 120 那条线。
   这正是 `dynPts` 建模的东西,而 dynPts 整体量到 0 —— 所以关卡特化版更不值。
   **明确决定不做**,理由记在这里。
