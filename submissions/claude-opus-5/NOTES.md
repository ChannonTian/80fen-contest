# NOTES —— 照着 RULES.md 写引擎时,规则书上的洞

按「照这份规则书能不能写出和裁判一致的引擎」来记。每一条都标出具体是哪一节哪一句、
我当时怎么理解的、为什么这么理解。排在前面的是**会导致实现不一致**的,后面是**费解但不致命**的。

---

## A. 会导致实现不一致的地方

### A1. §S2 ⑥ 说「打 25 墩」,但一局的墩数几乎从来不是 25

> §S2 ⑥:「打 25 墩:庄家领出;每墩四家各出一手;resolveTrick 定胜负;赢家领出下一墩」

我第一版照字面写了 `for (t = 0; t < 25; t++)`,第 21 墩崩在 `classify(undefined)`。
原因很简单:**只要有人领出对子或拖拉机,一墩就消耗每人 2 张以上,总墩数必然少于 25**。
实测自对弈平均一局 17~21 墩。

正确的终止条件是「手牌出完」,但规则书**没有任何一处写这件事**,§S5 也没有一条向量
覆盖「一局有几墩」。这是纯粹靠撞墙撞出来的。

连带影响 G 节的「最后一墩」:指的是**实际打完的最后一墩**,不是第 25 墩。
`lastLeadSize` 也是那一墩的张数。

**建议**:§S2 ⑥ 改成「打到手牌出完(单张到底时正好 25 墩)」,
并在 §S5 加一条向量:「全程单张 → 25 墩;第一墩领出一对 → 24 墩」。

### A2. 完全造反默认到底是开还是关,谁有资格喊

两处矛盾,而且是两个不同的矛盾:

**矛盾一:默认值。**
- `RULES.md` §I 参数表(第 371 行):「完全造反 | **默认关** | `off` / 仅重新发牌 / 完全造反」
- `RULES.md` §F(第 301 行)也写「可选规则,**默认关**」
- 但 `README.md` §3 `onRebel`:「定主之后,如果你手牌太差…**裁判会问你要不要掀桌重发**」,
  并且写死了「重发之后按无庄局处理」「同一局最多连重发 3 次」

README 是描述裁判**实际会调用的接口**的,它把这条规则讲得像是常开。

**矛盾二:谁被问。**
- `RULES.md` §S2 ④(第 448 行):「(可选)低分/少主造反:**任一家**满足阈值可要求重发」
- `README.md`(第 176 行):「**只有庄家的对方队会被问**,从庄家下家起问一圈,
  第一个说 `true` 的生效」

「任一家」包不包括庄家方?按 §S2 的字面是包括的。按 README 是不包括的。

**我的选择**:按 README 实现 —— 开启、「完全造反」模式、只问庄家的对方队、
从庄家下家起一圈、最多连重发 3 次。理由是 README 描述的是接口契约,
而我的 `onRebel` 只有在被问到时才有机会返回值,按 README 实现在两种读法下都不会出错。

**这条不是小事**:我量到「够格就重发」比「保守重发」好 +0.026 级/局(3.5σ),
比「从不重发」好 +0.065。重发会把这一局变成**无庄局**,给了下家抢庄的机会 ——
这是一条改变策略走向的规则,它的开关状态却是含糊的。

### A3. §S3 ③ `decompose` 的扫描是贪心的,会漏掉更长的拖拉机

> §S3 ③:「pairs 按 ordIdx 升序排;扫描 pairs:相邻两对若 ordIdx 差恰为 1 → 接进当前 run,
> 否则结束当前 run」

遇到**两个同序号的对子**时结果依赖扫描顺序。主 ♠ 打 2,手上
`♠A♠A`(ord 11)+ `♥2♥2`(12)+ `♦2♦2`(12)+ `♠2♠2`(13):

排序后是 `11, 12, 12, 13`。贪心扫描:11→12 接上,12→12 差 0 断开(得到二连对),
再 12→13 接上(又一个二连对)。结果是**两个二连对**。

但 11→12→13 明明能连成一个**三连对**(主A对 + 副级对 + 正级对,B 节明确说这两步都能连)。

我**照伪码字面实现**(切成两个二连对),因为规则书自己说「以下伪码与引擎逐行对应」。
但这意味着:

* 同一手牌「是不是拖拉机」取决于排序时同序号元素的先后,而不取决于牌本身;
* `isLegalFollow` 里的 `m`(本门最长拖拉机)会被低估 → 该跟的拖拉机可能判成不用跟;
* `canBeatComp` 判甩牌能不能被压,也跟着错。

§S5 里**没有任何一条向量**覆盖「同序号对子 + 相邻对子」的组合 ——
`P(H,2)+P(D,2)` 只测了两个同序号对子(throw),没测三个混在一起。

**建议**:要么把伪码改成「找最长链」(需要说明同序号的多个对子怎么择一),
要么在 B 节明确写「同序号的对子会打断链,这是有意的」,并补一条 §S5 向量。

### A4. §S3 ⑤ 没有保证「合法跟牌一定存在」

三条义务(张数 / 对子数 / 拖拉机)是**独立叠加**的。规则书没有说明它们永远可以同时满足,
而裁判在我跟错时要「替我出一手合法的」—— 这就要求存在性。

我不得不自己证一遍才敢写兜底构造(`moves.js: forceLegalFollow`):
设本门有 `n` 张、领出 `k` 张、`ns = min(k,n)`,必需拖拉机长度 `reqTr`、必需对子数 `must`,
则 `2·reqTr ≤ ns` 且 `2·must ≤ ns` 且 `reqTr ≤ must`,所以「先切一段必需拖拉机、
再补足对子、剩下用单张填」一定能凑出 `ns` 张。

**建议**:在 C 节末尾加一句「这三条永远可以同时满足」并给构造,
否则每个实现者都要自己踩一遍,而且很容易写出会死循环或抛异常的兜底。

### A5. 罚分封顶里的「满」没有数字

> `README.md` §4:「每局的罚分效果封顶在**这一局输光** —— 罚到闲家得分归零(或满)就不再往下罚了」

「满」是多少?牌面总分 200,但闲家总分算上抠底翻倍是可以超过 200 的(§S5 自己给了
75+40=115、35+80=115 的例子,理论上能到 200+8×20=360)。

我按 **把闲家的墩内得分截断到 [0, 200],再算抠底** 实现。
这个选择对我的策略没有影响(我不会故意犯规),但两个裁判实现很容易在这里分叉。

## B. 费解、但规则书其实说清楚了的地方(最难实现的几处)

### B1. 最难实现的一条:D 节「甩牌只看本门,不看谁能毙」

> §D:「判定只看**本门**,不看谁能毙。别人断门有主牌能毙,不影响甩牌成不成立」

意思是:`checkThrow` 通过 ≠ 这一墩赢得下来。一个「校验通过的甩牌」照样可能被
断门的人用主牌敲掉 —— 因为 `resolveTrick` 里主牌压副牌,只要结构签名对得上。

这两个判定用的是**两套不同的口径**(一个只看本门、一个跨门比),写的时候极容易
把 `checkThrow` 的结果当成「这一墩稳了」。我一开始的策略层就是这么错的:
`safeThrowOnly` 只检查本门有没有更大的牌,结果甩出去被主牌敲掉。

有意思的是:我后来加了「甩牌奖励乘以赢的概率」想修这个,**量出来反而差 4.5σ**。
甩牌被压不罚分(只强制出最小的一组),所以它本来就是一个**免费期权** ——
规则书把这条写清楚了(「不罚分」),但没有点出它的策略含义。

### B2. `rebelHappened` 的准确含义

README 只写「已经有人用王对反过 —— 之后不能再加固」。
是「有人**成功**用王对反了」还是「有人**尝试**过」?

我按**成功**实现(`declarationOf` 返回 strength ≥ 3,且通过了 `declAllowed`)。
§S5 只有一条「已发生造反 → 不可加固」,没有区分这两种读法。
一个返回了自己拿不出来的王对(记违规、当作没亮)的玩家,算不算「造反过」?按我的读法不算。

### B3. 无庄局里各家用**不同的级数**抢亮,强度却放在一起比

> §F:「无庄局里,各家按自己队伍的级数抢亮,谁亮到,这一局就打谁的级数」

于是会出现:A 队打 5,B 队打 2。A 亮 `♥5` 单张(strength 1),
B 用 `♠2♠2` 对子(strength 2)反掉 —— 两个「级数牌」根本不是同一张牌面。
`canOverride` 只比 strength 数字,不管级数。

规则书没有明说这样比是对的,但也找不到别的读法。我就按「只比 strength」实现了。
另外:A 亮完之后,如果 B 反掉,**这一局的级数从 5 变成 2**,
A 手上原来算作「主牌」的那些牌全部重新洗牌 —— 这一点规则书也没提,但按 §F 是必然结果。

### B4. README 把「无庄局」写成了「无主局」

> `README.md` §3 `onDeal` 最后一条:「**无主局**(`dealerKnown === false`)里你的级数是 `view.trumpRank`」

`dealerKnown === false` 是**无庄局**(没有预定庄家、要抢庄),
「无主局」是 `trump.suit === null`(王对造反成功或无人亮主)。两个完全不同的概念。
同一份 README 的 §8 第 2 条又正确地区分了它们(「`trump.suit === null` 才是无主局」)。
第一次读的时候我确实按「无主局」理解了一遍,回头对 §8 才发现不对。

## C. §S5 的自测向量够不够用

**结论:不够。它能保证「八个判定的单点行为一致」,但保不住「一局能不能跑完」。**

我实现里**写错过、而 §S5 没抓出来**的地方:

| 我犯的错 | §S5 有没有覆盖 |
|---|---|
| 一局固定打 25 墩 | **没有**。整张表没有一条关于「一局有几墩」的断言 |
| `decompose` 同序号对子的贪心断链(A3) | **没有**。只有两个同序号对子的 `throw`,没有「同序号 + 相邻」混在一起 |
| 甩牌校验通过 ≠ 这一墩赢下来 | **没有**。两条甩牌向量都只到「成功 / 失败被迫出最小组」为止,没有一条接着判这一墩谁收 |

除此之外,我认为还缺的向量(写对了纯属运气,不是被表逼出来的):

1. **`ordIdx` 在 `trumpRank = 14`(打 A)时的分支**。表里所有向量都是打 2 或打 7,
   `rank < trumpRank ? rank-2 : rank-3` 这个分支只被走了一半。打 A 时 `♠2` 应当是 0、`♠K` 是 11。
2. **`resolveTrick` 里后手出了混门牌**(`classify` 返回 `null`)。
   现有向量里 `♥6♥7` 是同门不同点的 `throw`,不是混门。混门返回 `null` 要走另一条分支。
3. **`min(领出张数, 本门张数)` 与对子义务同时生效**:
   S6 第 5 条用文字说了「本门 5 张、领出 2 张时出 2 张即可」,但没有对应向量;
   「本门 5 张里有 2 个对子、领出 1 对」这种要不要出对,也没有向量。
4. **`countPairsIn` 数的是不相邻的对子**。伪码专门强调「不看是否相邻」,但没有向量。
5. **甩牌失败时被迫出的是「`top` 最小的一组」而不是「张数最少的一组」**。
   S6 第 10 条用文字点了名,`P(H,Q)+[H,J]` 那条向量里最小的恰好也是单张 ——
   **正好是这条规则想警告的反例没被测到**。应该补一条「甩 `♥3♥3 + ♥A`,被压 → 强制出 `♥3♥3`」。
6. **闲家总分超过 200**(抠底翻倍 ×8)时 `scoreRound` 的升级数。
7. **`advanceMatch` 在 `up = 0`(闲家 80–119)且该队正卡在关卡上**:
   只换庄不升级、`played` 不动 —— 现有向量里 80–119 那条没带关卡。
8. **加固之后再被别家王对反掉**,`curDecl` 的 seat / suit / strength 应该变成什么。

## D. README 里容易让人误解接口的地方

1. **`declSeat` 这个名字**。字段表写「`declSeat` | `0..3｜-1` | **庄家**」,
   但名字读起来像「亮主的那一家」。在庄定局里亮主者和庄家是两个人(§S5 定庄那一节
   专门测了这件事),名字和语义是反的。建议改叫 `dealerSeat`。
2. **`dealer` 和 `declSeat` 并存**,字段表说 `dealer` 是「本局庄家(无庄局为 -1)」,
   `declSeat` 也是「庄家」。两个字段同名不同义,只能靠 `deal 阶段恒为 -1` 这句话反推
   `dealer` 是「发牌前就定好的庄家」、`declSeat` 是「定完主之后的庄家」。
3. **`onDeal` 一局被调用 100 次 + 最多 4 圈**,但没说这 4 圈里 `view.hand` 已经是 25 张。
   §8 第 10 条只说了「deal 阶段的 `view.hand` 只有已经发到的牌」,
   容易让人以为收尾那几圈也是不完整的。
4. **`lead` 可以返回 `Card[]` 或 `{cards: Card[]}`,`follow` 只写了返回 `Card[]`**。
   我两边都做了兼容,但规则上 `follow` 能不能返回 `{cards}` 没写。
5. **「甩牌被吃 → 罚 0」这一行**放在罚分表里,容易让人以为甩牌是一种违规。
   实际上它是规则内的合法赌博(D 节写得很清楚),放在罚分表里反而误导。

## D2. 最严重的一个洞:淘汰门槛的分母没有定义

README §时间(第 78 行):

> 每次调用都计时……**超出基准选手 3 倍的提交不进决赛**。

这是全篇唯一一条**硬性淘汰**条件 —— 违反它不是扣分,是出局。但**「基准选手」
在提交截止之前是不可知的**。README 第 255 行只说「我们会安插一个基准选手一起
打,它和你们一样受同样的规则约束」,没有给出它的实现、复杂度档次,也没有给出
任何可以自查的数字(比如「基准选手在参考机器上每次决策约 N µs」)。

于是一条硬性门槛变成了一个无法自查的条件。我能做的只有推断下界:

* 如果基准选手是「合法但无策略」那一档(我的 `naive`,约 1.3µs),3× ≈ 3.9µs,
  那么连一个只做静态估值的简单 bot(我的 `greedy`,约 12µs)都过不了。
  这会让规则变成「任何认真思考的程序都出局」,不可能是本意。
* 所以我按「会思考的简单 bot」这一档定标,目标 ≤3×,并留了 35% 余量。

**这个洞的代价是真实的**:我为它花掉了这一轮的绝大部分时间,做了七处纯提速
(把 ~2.8× 压到 ~1.95×),而这些工作**对棋力零贡献**。如果 README 给出一个
可自查的数字,或者干脆把基准选手的代码放进 `example/`,这些时间本可以花在
棋上。

顺带一提,这条规则还有三处没说:

1. **计时口径没说。** 是 wall clock 还是 CPU 时间?我实测过,在有争用的机器上
   两者能差出一倍以上,而且 wall clock 下**比值本身会被争用推高**(调用越长
   越容易被中途调度出去)。同一份代码我先后量到 2.76× 和 3.90×。
2. **「总用时」怎么归一没说。** 是总秒数,还是每次调用的平均?如果是总秒数,
   那么一个下得更快结束对局的选手会占便宜 —— 而这和棋力是相关的。
3. **JIT 预热算不算。** 一个 25 行的 bot 第一次调用就是稳态;我的代码前几百次
   调用要慢好几倍。如果裁判只跑一遍不丢弃前若干次,重的提交会被系统性高估。

`example/` 里也没有任何和时间有关的东西可以对表。

## E. 一句总结

八个判定里,**`decompose`(A3)最难写对**,因为它同时被 `classify`、`isLegalFollow` 的
最长拖拉机、`checkThrow` 的 `canBeatComp` 三处依赖,错一点会从三个方向渗出来,
而 §S5 对它的覆盖恰好绕开了唯一有歧义的情形。

第二难的是**「一局有几墩」**(A1)—— 它根本不在规则书里,只能靠跑崩了才知道。

## F. 补充:无主局这条路径,规则书和自测向量都覆盖得最薄

自对弈里我的 AI 从不主动打无主(实测「用王对反成无主」是 −0.017 级/局,不划算),
于是**无主局在自对弈里的出现率是 0.0%** —— 一条完全没被练到的代码路径。
但联赛里对手只要有一对王就能把这一局变成无主,所以我专门写了压测
(`dev/ntstress.js`:逢王对必反的对手 800 局 + 全场不亮主强制无主 300 局 + 极端手牌)。

回头看规则书对这条路径的覆盖:

* §S5 关于无主局只有 **4 条**向量,全是 `effSuit` / `ordIdx` / 拖拉机连不连得上,
  **没有一条**关于无主局里的跟牌义务、一墩胜负或结算;
* A 节写「无主局四门级数牌一律同级(13),同级相碰先出的那家大」——
  这是**整份规则书里唯一会真正撞上「平手」**的地方(S6 第 7 条也这么说),
  但 §S5 里**没有一条向量真的构造两家出同级异花级数牌**去验「先出者胜」。
  E 节的四条向量里那条无主局的例子(`♥5 / ♠A / ♥6 / ♦A`)恰好避开了它。

**建议**至少补两条:
1. 无主打 2:领出 `♠2`,第二家出 `♥2`,第三家出 `♦2` → **领出方赢**(全是序号 13,先出者胜);
2. 无主打 2:领出 `♥5`,某家用 `♠2` 毙 → 主牌(级数牌)压副牌。

另外一处「规则说清楚了、但我实现时踩了」的地方:**`decompose` 在无主局里对
异花级数牌的处理**。`P(H,2)+P(D,2)` 在无主局是 throw(两对都是序号 13,差 0 不相邻),
而 `P(H,2)+P(小王)` 是 tractor(13→14)。这两条 §S5 都有,写得很好 ——
但它们和 A 节「四门级数牌一律同级」放在一起才能推出「无主局里级数牌对子之间永远连不上,
只能往小王那一档接」,规则书没有把这句话直接写出来。

## G. 一处「规则书没错、但接口设计会掩盖错误」的地方

README §4 规定:抛异常时裁判替你出一手合法的,按张数罚分。这个设计对**规则违例**是对的,
但它对**策略层的崩溃**是静默的 —— 因为我自己也在 `makeAI` 里用 `try/catch` 兜底,
返回一手保证合法的牌,于是:

* 裁判看到的是合法着法,**不记违规、不罚分**;
* 我自己的合规检查(几千局零违规)**全绿**;
* 而实际上我的跟牌逻辑每一手都在抛异常,棋力掉了 0.57 级/局。

这一轮我真的踩了这个坑,靠「对固定外部参照跑分」才发现(自对弈 A/B 对两边一起退化失明)。

**给规则书/裁判的建议**:如果裁判能在成绩单里公示「替某位选手出牌的次数」
(哪怕不罚分,比如选手自己返回了合法牌但抛过异常的情况无法区分),
或者干脆建议选手**不要在最外层无差别 try/catch**,会少掉一大类隐形故障。
现在的口径下,「一手 bug 罚 5 分」这句话给人的印象是「崩溃会被罚分暴露」,
但只要选手自己兜底得足够好,崩溃就是完全隐形的。

这不是规则书写错了,是**接口的失败模式设计**让一类严重故障不可观测。
